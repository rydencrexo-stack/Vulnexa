Task 01 · Conceptual Overview

Understanding Insecure Direct Object References

Insecure Direct Object Reference (IDOR), also classified as Broken Object Level Authorization (BOLA), occurs when an application exposes a reference to an internal database object in a request parameter, and fails to verify whether the requesting user has permission to access that object.

Common examples include changing an invoice ID in a URL (/invoice?id=1001 to /invoice?id=1002) to view another customer's private financial data.

Core Vulnerability Rule

Authentication verifies who the user is; Authorization verifies what resources that specific user is permitted to view or edit.

Task 02 · Authorization Pitfalls

The Fallacy of Obscurity (UUIDs vs Access Control)

A common developer misconception is that replacing sequential IDs (1, 2, 3) with random UUIDs (7b4e28-4a...) solves IDOR vulnerabilities.

While UUIDs make brute-force enumeration harder, if an attacker acquires a victim's UUID from a public profile, chat, or shared link, the application will still serve the victim's private data if server-side authorization checks are absent.

Why does using random UUIDs alone fail to eliminate IDOR vulnerabilities?
Because the backend still lacks an authorization check verifying that the session user owns the requested object.
UUIDs can only store numbers.
UUIDs expire after 24 hours.

Task 05 · Remediation Controls

Implementing Robust Ownership Verification

To defend against IDOR, applications must enforce resource ownership at the data layer:

  • Scoped Database Queries: Always include the authenticated user ID in the query filter (e.g. WHERE id = :docId AND user_id = :sessionUserId).
  • Role-Based Access Control (RBAC): Validate tenant permissions before returning object representations.
Which database query design pattern effectively mitigates IDOR at the query layer?
